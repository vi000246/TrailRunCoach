# 圖表改由裝置用逐秒資料自己畫，值不值得做（SP-325）

> 調查日期：2026-10-15。只做調查與原型，沒有改正式程式。程式版本 `integrate/2026-10-12a` `7e5fb7e0`。
> 相關：`fit-on-device.md`（SP-319 §9.1、§12 單 10）、`cache-tiering.md`（SP-320，NAS 倍率 × 8.5）、`local-first-sync.md` §8.1（SP-315：逐秒資料從自己的伺服器拿）、SP-314（離線快取，`offline_core.js` 的 p2 還空著在等這張）、SP-313（手機瀏覽器解析 FIT，另一個 agent 在做，本文沒有重複量）。
> 標記：**已驗證**＝讀程式或實測；**推估**＝由量測換算或判斷；**未量**＝沒有量到。
> 資料：全部用示範跑者（`backend.demo.build --weeks 52`，257 筆活動），沒有讀 NAS、`.env`、金鑰。本機是 Apple M5 Pro；「NAS 推估」＝本機 CPU 秒 × 8.5。「手機」是 Chromium 把 CPU 降速 4 倍／6 倍模擬，**不是真手機**。

---

## 0. 結論

1. **不建議為了省伺服器成本做這張。** 能搬到裝置的 4 張圖（心率與功率、心率趨勢、心率區間、功率區間）只占單次活動頁第一次打開 CPU 的 5–10%。每筆活動 NAS 約省 1 秒 CPU；1,000 位會員一天合計約 12 CPU 分鐘，**不到每次同步失效鏈（SP-320：每筆 130–145 秒）的 1%**。推估（CPU 已驗證）。
2. **單上的前提有一半不成立：伺服器本來就不產生圖片。** 所有圖表本來就是裝置用 ECharts 畫的。伺服器算的是「畫圖用的 JSON」，存在 `cache/render`（每個租戶上限 300 MB）。已驗證。
   - 擁有者整個 `cache/render` 只有 4.4–4.8 MB（SP-319、SP-320）。
3. **使用者不會覺得變慢，反而比較快，但差距只有幾十到幾百毫秒。**
   - 裝置自己算 4 張圖：桌面 0.2–1.2 ms，模擬手機（6 倍降速）1.5–7.8 ms。
   - 畫圖（ECharts）的時間兩種做法一樣：桌面 4–5 ms，模擬手機 15–46 ms。
   - 要下載的資料比較少：5 秒一點加 GPS，每筆 gzip 後 8–43 KB。現在這 4 張圖加 `/samples` 要 71–113 KB。
   - 已驗證（原型）。
4. **真正的好處是離線和少傳資料，不是省成本。**
   - 現在離線完全看不到單次活動的圖（SP-314 p2 是空的）。
   - 如果直接把伺服器回的 JSON 存在裝置上：一筆活動整頁約 300 KB，近 90 天（示範 71 筆）約 23 MB，超過 20 MB 預算。改存畫圖資料：近 90 天 1.5–5 MB。
5. **核心算法不能搬，搬了也沒用：單次活動頁 25 張圖裡有 19 張是判讀卡，要用核心。** 能搬的 4 張只用公開的公式（30 秒平均、NP、區間時間、線性回歸），而且這些公式現在就在公開版的 `activity_charts.py` 和 `charts.html` 裡。所以搬過去不會多公開任何東西。
6. **建議：把 SP-325 改成三張小單，「裝置自己算」先不做，等使用者決定（§7、§8）。**
   - (A) 心率與功率圖改送「每段的增量」：gzip 後少 58–77%，畫面不變。
   - (B) Service Worker 把看過的活動圖存起來，離線也能看：伺服器零額外成本。
   - (D) `/samples` 補上會員範圍檢查。
   - 如果之後要「近 90 天每筆都能離線看圖，不用先打開過」，再做 (C) 畫圖資料 API 和裝置端畫圖。格式用跟 `/samples` 一樣的步長（最多 3000 點），**不要用固定 5 秒**：短的課表會比現在粗，30 秒最高功率可能差到 17 W。
7. **附帶發現：打開一筆活動真正慢的是判讀卡，不是畫圖。**
   - 伺服器剛啟動後第一次打開活動：「跑姿」和「重點數字」兩張判讀卡要建整份資料的基準，本機 10.5 秒，NAS 推估約 90 秒。
   - 之後每筆活動第一次打開，25 張合計本機 0.95–1.66 秒（NAS 8–14 秒）。
   - 這要在 SP-320／SP-303 處理，跟 SP-325 無關。

## 3. 畫圖資料要多大（已驗證，示範資料）

格式：時間（秒）加各通道，float32、小端、按欄存。示範跑者近 90 天有 71 筆、105 小時；擁有者是 54 筆（SP-319）。

| 格式 | 每筆（4 個樣本）原始／gzip | 近 90 天原始／gzip | 近 1 年（258 筆）原始／gzip |
|---|---|---|---|
| 5 秒，時間＋心率、功率、速度、海拔（單上的格式） | 10–55／4–24 KB | **1.52／0.62 MB** | 5.61／2.28 MB |
| 5 秒，再加距離、經緯度 | 16–88／8–43 KB | 2.43／1.17 MB | 8.98／4.28 MB |
| 跟 `/samples` 同步長（最多 3000 點；50 分鐘以內是 1 秒），時間＋5 通道 | — | **3.73／1.73 MB** | 13.6／6.27 MB |
| 同上，再加經緯度 | — | 4.98／2.24 MB | 18.1／8.13 MB |
| 1 秒，時間＋5 通道 | 59–329／26–138 KB | 9.11／3.72 MB | 33.7／13.6 MB |
| 對照：伺服器現在的整頁 JSON 全部存裝置 | 290–360／88–122 KB | 約 23 MB（推估） | — |

- **斷點要保留。** 原型匯出時把暫停時段補成連續的，兩筆越野跑的心率區間時間就和伺服器差了 885–898 秒。伺服器的做法是超過 30 秒沒資料就當斷點（`activity_charts.py` 的 `_on_grid`）。畫圖資料格式要把斷點標成 NaN。

## 4. 裝置自己算、自己畫要多久（已驗證，原型）

原型：`docs/research/device-side-charts/proto.html`，ECharts 5.6.0 從 cdnjs 載入，跟 `charts.html` 一樣。

- **裝置路徑：** 從 Cache API 讀畫圖資料 → 解碼 → 算 4 張圖（30 秒功率、每段平均、11 種累計值、心率與功率區間、心率 60 秒平滑與趨勢線） → `setOption`。
- **伺服器路徑：** 伺服器的 4 個 JSON（已經在瀏覽器裡）→ `JSON.parse` → `setOption`。
- 兩條路徑畫的圖完全一樣。每組跑 5 次取中位數。Playwright 的 Chromium（headless）；手機是 390×844 視窗加 CDP `Emulation.setCPUThrottlingRate`。

| 環境 | 讀 Cache API | **裝置計算**（5 秒／1 秒資料） | 伺服器 JSON 解析 | `setOption`（兩條路徑相同） | 畫到螢幕上（兩個 frame） |
|---|---|---|---|---|---|
| 桌面 | 0.4–0.7 ms | **0.2–0.5／0.4–1.2 ms** | 0.2–0.4 ms | 4–5.5 ms | 約 33 ms（被 60 Hz 卡住） |
| 模擬手機 4 倍降速 | 1.3–2.0 ms | **1.4–2.1／2.3–4.8 ms** | 0.7–1.7 ms | 15–27 ms | 31–34 ms |
| 模擬手機 6 倍降速 | 2.2–3.3 ms | **1.5–3.4／3.5–7.8 ms** | 1.5–2.2 ms | 28–46 ms | 35–55 ms |

**使用者看到的時間（推估，以「心率與功率」一張圖為例）：**

| 情況 | 現在 | 裝置自己畫 |
|---|---|---|
| 看過的活動再打開 | NAS 0.04–0.17 秒＋來回延遲（未量，透過 Cloudflare Tunnel 推估 50–150 ms）＋下載 38–56 KB | 畫圖資料在裝置上：約 40–60 ms，**離線也可以** |
| 第一次打開 | NAS 約 0.3–0.4 秒，但同一分頁的「重點數字」判讀卡要先排隊（伺服器同時只算 2 張）；伺服器剛啟動後第一次要等更久（§0 第 7 點） | 畫圖資料不在裝置上：下載 8–43 KB（10 Mbps 約 0.03 秒，山區 2 Mbps 約 0.17 秒），加上不到 10 ms 計算。現在這 4 張圖加 `/samples` 要下載 71–113 KB（山區約 0.4 秒） |
| 沒有網路 | 看不到 | 看得到這 4 張圖、地圖旁的圖；判讀卡要另外快取（單 B） |

**結論：裝置計算加起來不到 10 ms，畫圖的時間兩邊一樣，要下載的資料比較少。所以不會變慢。** 但頁面上的判讀卡仍然要等伺服器，整頁感覺的速度主要由判讀卡決定。

## 5. 5 秒一點會不會讓數字或圖變得不一樣（已驗證，4 筆示範活動）

比較同一份資料用 1 秒和 5 秒算出來的結果：

| 數字 | 差多少 |
|---|---|
| 平均心率 | ≤ 0.05 bpm |
| NP | ≤ 0.4 W |
| 最高心率 | 一樣（示範資料比較平滑；真實資料的尖峰在 5 秒取樣時可能被跳過，推估） |
| 30 秒最高功率 | −1.8 到 **+17 W**（5 秒資料的 30 秒視窗只有 6 個點） |
| 心率區間時間 | 最多差 47 秒（整趟的 1.3%） |
| 功率區間時間 | 最多差 2 分鐘 |
| 心率趨勢斜率 | 差 0.2 bpm／小時（1–2%） |
| 移動時間 | ≤ 9 秒 |

- **圖會變粗。** 伺服器現在每張圖最多 1500 點，每點 1–10 秒。2 小時以內的活動現在是 1–4 秒一點；改成 5 秒一點，41 分鐘的活動只剩 494 點（現在 1233 點），15 秒的衝刺、30／30 間歇會被抹平。
- **所以「看起來跟現在一致」這條驗收用 5 秒做不到。** 要用跟 `/samples` 一樣的步長：最多 3000 點，所以 50 分鐘以內是 1 秒，4 小時是 5 秒。

## 6. 哪些圖可以在裝置畫，哪些要伺服器算好

| 圖或資料 | 放哪 | 理由 |
|---|---|---|
| 心率與功率（含拖曳選段統計）、心率趨勢、心率區間、功率區間 | **可以搬到裝置** | 用到的公式是 30 秒平均、Coggan NP、區間計時、最小平方法、標準差，都是公開的；這些現在就在公開版的 `activity_charts.py` 和 `charts.html`（`ACT.stats`）裡，搬過去不會多公開任何東西 |
| 地圖旁的圖、同步游標 | 已經在裝置 | `charts.html:2165`、`:2447` |
| 門檻（AeT、LTHR、CP）、區間邊界（含 COROS 三種模型） | **伺服器算好，隨畫圖資料一起送數字** | 門檻是估算出來的（核心）；邊界由 `_bounds` 和 `hr_profile` 算 |
| 心率可能不準的段落（`hr_quality`） | **伺服器算好，送段落** | 要原始取樣加步頻；輸出很小 |
| 19 張判讀卡（重點、飄移、間歇、W′ 電池、CP 測驗、爬坡、耐久、跑姿） | **伺服器（核心）** | `workout_review`、`interval_eval`（照 WKO5 dfrc 重建，公開版不放）、課表分類 |
| 路線難度 | **伺服器（核心）** | wko5expr 運算式 |
| FIT 轉成各通道 | **伺服器（核心）** | `files/fit_to_channels.py` 公開版不放。裝置拿到的是已經轉好的通道，不在裝置解析 FIT |
| 多筆活動的區間時間（`period_zones`） | 伺服器 | 用的是同一份 `activity_charts.grid`／`_bounds`（`period_zones.py:46`）。搬了單筆的圖之後，Python 版還要留著，**會變成兩份實作**，要用 node 測試對 Python 參考實作比對 |

**對公開鏡像的影響：**

- 搬的 JS 會放在 `backend/static`，在公開版裡，任何人打開網頁也都看得到。
- 只限上面「可以搬」那幾張就沒有新的公開內容。
- 畫圖資料 API 要用 Dataset（核心），在公開版會跟現在的圖表一樣回 503，不影響。

**對商業化的影響：**

1. **免費方案的「圖表每天 5 個」和「近 90 天」**（`membership.py:123`；檢查在 `wko5views.py:836-837`）只在伺服器算圖時檢查。裝置用快取自己畫，伺服器就數不到。做法：下載畫圖資料時檢查範圍並扣額度，之後重看裝置上的快取不再扣（要使用者決定，§8 Q4）。
2. **已經有的漏洞：`GET /workouts/{idx}/samples` 沒有任何會員檢查**（`wko5views.py:1918`）。免費會員可以拿到任何日期活動的逐點心率、功率和 GPS。建議補上（單 D）。
3. 判讀卡是付費價值所在，留在伺服器。

## 7. 建議開的單

## 8. 要使用者決定的問題

1. **SP-325 要不要做「裝置自己算圖」？**
   - (a) 不做。關掉 SP-325，改開 A、B、D（加 E）。**建議選這個**：伺服器省不到 1%，使用者在意的「離線看得到」用 B 就有了，而且 B 連判讀卡都能離線看。
   - (b) 做 C（在 A、B、D 之後）。好處是近 90 天每筆活動不用先打開過，離線也能看 4 張圖。代價是 Python 和 JS 兩份實作要一起維護。
   - (c) 照原單做（固定 5 秒）。不建議：短的課表會比現在粗，30 秒最高功率可能差到 17 W。
2. **如果做 C，畫圖資料要多細？**
   - 固定 5 秒：示範近 90 天 1.5 MB，擁有者約 1.0 MB。
   - **跟 `/samples` 同步長**：示範 3.7 MB，擁有者約 2.8 MB。**建議選這個**，看起來跟現在一樣。
   - 固定 1 秒：示範 9.1 MB。
3. **離線要能看到哪些活動？**
   - 只有看過的（B）。
   - 近 90 天全部，但只有 4 張圖和地圖（C）。
   - 兩個都要。
4. **免費方案「圖表每天 5 個」怎麼算裝置上的圖？**
   - (a) 只在第一次從伺服器拿資料時扣，之後在裝置上重看不扣（**建議**，離線本來就沒辦法回報）。
   - (b) 每次打開都要回報伺服器，沒網路就不能看。
5. **`/samples` 現在沒有會員檢查，要不要補（單 D）？** 建議補。現在免費方案可以拿到任何日期活動的逐點心率、功率和 GPS。
