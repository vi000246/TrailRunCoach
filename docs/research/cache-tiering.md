# 快取分級與增量重算：新增或刪除活動時只重算受影響的部分（SP-320）

> 調查日期：2026-10-07。只做調查，沒有改程式。程式版本是 main `35efbe3c`。
> 相關單：SP-317（超過 3 年的活動每月封存刪除）、SP-308（FIT 改成 sha256 命名的不可變物件）、SP-311（每個租戶的資料分類表）。SP-319（FIT 存在使用者裝置上）由另一份文件處理，這裡不重複。
> 標記：**已驗證**＝這次讀程式、實際跑量測或讀正式 log 確認；**摘要**＝引用別的文件或程式註解裡的說法，這次沒有重跑；**推估**＝根據量測延伸算出來的數字或我的判斷；**未找到來源**＝查不到、也量不到。
> 本文只放彙總數字（筆數、秒數、MB），不放擁有者個人的生理數值。

## 摘要

1. **FIT 解析已經是逐筆增量，不是瓶頸。** 新增一筆活動時，資料集本身只要解析那一筆。本機量測：加回一筆後資料集加門檻估算共 0.3 秒；刪掉全部 171 筆三年以上的舊活動，重建也只要 1.0 秒（已驗證，本機）。
2. **慢的是上層：它們的快取 key 是「整份資料」或「整個程式模組」的簽章。** 這些地方有一點改動就整份重算：
   - 活動自動分類：key 包含整份活動清單，加上 9 個模組的原始碼雜湊。
   - 圖表渲染快取：key 包含整份活動清單、`today`，以及引擎所有 .py 檔的 mtime。
   - 門檻估算記憶（`estimate.json`）和 PD 重擬記憶（`pd_mftp.json`）：key 包含整個 `racepower/athlete.py` 等模組的原始碼。
   - 總覽狀態和課表快取：key 是 Dataset 物件的 `id`。
3. **部署很頻繁，版本常升。** 兩週內：
   - 773 個 commit 裡有 430 個動到引擎，每一個都讓圖表快取全部失效。
   - `racepower/athlete.py` 改了 39 次，每次讓 PD 重擬全部重做。
   - `workout_review` 的 `CACHE_KEY` 從 v14 升到 v23，每次 807 筆全部重量。

   正式環境 log 裡有 6 次啟動，「資料集建置」花 1.5～30.2 秒，「暖機」花 29.5～175.9 秒；圖表請求平均 11.6 秒，最久 59.7 秒（已驗證，log）。
4. **常用資料都在近一年內。** 擁有者 807 筆活動中，近 90 天 54 筆，91～365 天 165 筆，一年以上 588 筆（已驗證）。一年以上的活動對今天 CTL 的影響小於萬分之二，三年以上的影響小於 10⁻¹¹（推估，用 42 天時間常數計算）。所以刪舊活動完全不需要動到近 90 天和近一年的快取。
5. **建議的做法分成四塊：**
   - **分層 key**：逐筆結果用「檔案雜湊＋該欄位的版本」當 key。跨活動彙總用「時間段（月）」分段，不用整份簽章。
   - **分級**：熱資料是近 90 天，同步時就算好。溫資料是近一年，在背景補算。冷資料是一年以上，用到才算，或用月摘要。
   - **背景補算**：版本升級後由新到舊慢慢補，補完之前先顯示舊值並標「更新中」，第一次開頁面不會被卡住。
   - **排程**：重建工作放進全域佇列，限制同時跑的數量，部署後錯開。

   目標等待時間見 §5；效益排序和建議的單見 §6.2。

## 1. 現況

### 1.1 量測方法

- **資料**：從 NAS 唯讀複製擁有者的 812 個 FIT（119 MB）到本機暫存區（已驗證）。秘密檔（`secret.key`、`.env`、token）都沒有碰。
  - 我原本要複製一份**移除 token 後**的 DB 副本，但被權限擋下。原因是 DB 裡的 `sync_state` 表含有加密的 token。
  - 所以本機量測**沒有** DB 和 plan：門檻全部來自 FIT 的自動估算，也沒有課表、測驗紀錄、使用者標記。正式環境的估算輸入比本機多，實際花的時間會更長。
- **環境**：
  - 本機是 Apple Silicon，18 核心，用 repo 的 `.venv`。
  - 用 `WKO5COACH_FIT_WORKERS=2` 模擬 NAS 預設的 worker 數：NAS 有 4 核心，`_pool_size` 算出來是 min(8, 4−2, n/4) = 2。
  - 腳本在 session 暫存區（`bench.py`、`bench2.py`、`bench3.py`），每一步都用新的 process 計時。
- **NAS**：Intel Celeron J4125（4 核心，2.0 GHz），記憶體 10 GB（已驗證，`/proc/cpuinfo`）。
  - 我原本想在容器裡跑同一份腳本，取得真實的速度倍率，但這個動作也被權限擋下。
  - 所以本文的「NAS 推估」一律用 **本機 × 4～6**（推估，依兩顆 CPU 的單執行緒等級）。這個倍率是本文最大的不確定處，見 §7 第 1 條。
- **正式 log**：讀 `data/logs/app.log`（2026-10-06 12:26 到 10-07 08:53，共 287 行），以及 `docker logs trailruncoach`。只看 `slow`、`took` 開頭的時間行（已驗證）。

## 2. 落差與發現

### 2.1 解析已經是增量的，問題在上層的 key（已驗證）

`fitcache.py` 的設計已經符合 SP-320 想要的方向：

- 逐檔有效。
- 每個欄位帶自己的版本。
- 檔案不見時清掉那一筆。
- 內容沒變、只有 mtime 改變時用 sha1 認出來。

所以「同步一筆」和「刪舊活動」在**資料集這一層**已經很快：本機 0.3～1.0 秒，NAS 推估 1.5～6 秒。

慢的是它上面那幾層，有四種情況：

1. **用整份資料當 key**：活動自動分類的 `signature()`、圖表的 `data_fingerprint()`、門檻估算的 `_estimate_key()`。少一筆或多一筆，整份重算。
2. **用 `id(ds)` 當 key**：狀態、課表、racepower 的記憶體快取。每次同步都換一個新的 Dataset 物件，所以這些快取每次都清空。
3. **用 `today` 當 key**：圖表、門檻估算、racepower。每天第一次打開都要重算。
4. **用「整個模組的原始碼」或「所有檔案的 mtime」當程式版本**：PD 記憶雜湊 `athlete.py` 整個檔（將近 2,000 行），圖表雜湊整個引擎目錄的 mtime。改一行文字說明也會讓全部重算。

### 2.2 部署頻率讓「版本升級整份重算」變成常態（已驗證，git log）

2026-09-23 到 10-07 共 773 個非 merge 的 commit：

| 檔案或目錄 | commit 數 | 影響 |
|---|---|---|
| 引擎任何檔（`backend/engine`、`backend/files`、`api/wko5views.py`） | 430 | 圖表快取全部失效（mtime 簽章） |
| `engine/workout_review.py` | 64 | 自動分類全部重算；`CACHE_KEY` 從 v14 升到 v23，共 10 次 |
| `engine/racepower/athlete.py` | 39 | PD 重擬全部重做、估算 key 失效、自動分類全部重算 |
| `engine/wko5expr/fitdataset.py` | 28 | 動到 `workout_fields` 或 `averages_of` 時，FitStore 的那個欄位重算 |
| `engine/activity_tags.py` | 19 | 自動分類全部重算 |
| `engine/thresholds.py` | 11 | 估算 key 失效、自動分類全部重算 |

log 裡 6 次部署有 4 次的資料集建置是 26～30 秒，另外 2 次是 1.5 秒和 7.1 秒。這跟「這次有沒有改到 athlete、thresholds 這幾個模組」的分佈相符（推估：log 沒有記錄每次部署是哪個 commit）。

### 2.3 時間窗：常用的圖只看近一年，但有些計算從第一天算起（已驗證＋推估）

- 圖表預設範圍是 **365 天**（`wko5views._range`：`b = e − 365`），不是 90 天。
- PMC 類的運算（`ctl`、`atl`、`tl(...)`）要從歷史第一天開始累積：
  - `pmc-all` 本身很便宜，0.02 秒。
  - 但 `tis-load`（`tl(tisaerobic, ctlconstant)` 等 4 條）在逐筆值已暖時還要 2.2～3.7 秒，而且 **90 天和 365 天的範圍一樣慢**（本機）。代表成本不是由時間窗決定，而是每次都把每筆活動的 TIS 從頭累加，熱點在 evaluator 裡（推估，沒有做 profiling，見 §7）。
- **舊活動對今天幾乎沒有影響**：CTL 的時間常數是 42 天，一筆活動對 d 天後的 CTL 權重是 e^(−d/42)（推估，指數加權平均的定義）：
  - 90 天：0.12
  - 365 天：1.7×10⁻⁴
  - 3 年：約 5×10⁻¹²

  所以刪三年前的活動，近 90 天和近一年的 PMC 在顯示精度下完全不變。但現在的 key 設計還是會讓這些圖全部重算。
- 最佳成績（mean-max）：`run-power-recent-bests` 這類圖只看「近 90 天」和「近 7 天」。冷算時 4.8 秒，主要是逐筆的 mean-max 曲線；暖了以後接近 0 秒（本機）。

### 2.4 磁碟會一直長大（已驗證，NAS `ls`）

- 舊版的 `series_*` 檔不會被刪。NAS 上 59 MB 的 `series_*` 裡，約 43 MB 是 v18、v19 的舊檔，最大一個 22.8 MB。
- 成就快取不會清掉已刪除的活動。
- `mmp_cache` 和 `channel_peaks`、`workout_curves` 沒有程式版本，改了計算方法也不會更新（讀程式）。
- 以上都應該放進 SP-311 的「衍生資料」分類，由 SP-317 的清理流程一起處理。

### 2.5 記憶體與並行（讀程式＋log）

- **同步後最多會同時建兩個 Dataset。** 同步後校正固定呼叫 `_dataset(False)`（`calibrate.py:250`），而 `plan_auto`、暖機用的是預設模式。如果 `engine.json` 的 parity 是 true（有 WKO5 資料夾時的預設），兩者的 key 就不同，會建出兩個 Dataset（讀程式；NAS 上 `engine.json` 實際是哪個值，這次沒有讀）。
  - 一個 FIT Dataset 在圖表都跑過之後是好幾百 MB（摘要，`_DatasetCache` 註解）。
  - 2026-10-05 卡在「第 9／17 筆」，很可能就是兩次整份重建，加上 process pool 的記憶體壓力（推估）。
- **重建沒有全域上限。** 只有「同一個 key 只建一次」（single flight）。暖機只幫**目前租戶**（擁有者）暖，`DATASETS_MAX=2` 是全部租戶共用：100 位會員輪流開頁面時會互相擠掉，每次都重建（推估）。
- **狀態和課表快取沒有 single flight**：同時兩個請求都沒命中時，會各算一次（讀程式）。
- 兩個多租戶時會出錯的 key：
  - `plan_sessions._cache` 的 key 沒有租戶（雖然有 `id(ds)`，實際上大多能分開）。
  - racepower 的 `hrc_test` **只用今天當 key**，會把 A 的結果給 B。

  這是正確性問題，不只是效能問題（讀程式）。

### 2.6 同步本身的時間大多不在快取（已驗證，log）

- 3 次同步中，「列出活動」占 33～54 秒，每次都檢查全部 819 筆。
- 「收尾」有一次 64.6 秒。

這兩段都不是快取能解決的，放到 §7 給 SP-303。

### 3.1 分層與依賴圖

```

                      │
L1 逐筆衍生      FitStore 解析欄位 ──► series_*（判讀、racepower、門檻逐筆、mean-max…）

                      │
L2 跨活動彙總    ┌ 全歷史累加：PMC、tl(TIS)、CTL 起點           ← 便宜，可每次重算
                 ├ 滑動窗：PD 重擬（90 天）、門檻估算（格點日）、最佳成績窗（90 天／7 天）
                 └ 全量掃描：自動分類（目前）、成就聚類、狀態
```

### 3.2 每個快取屬於哪一類

| 類型 | 快取 | 新增 1 筆**應該**影響的範圍 | 刪 1 筆**應該**影響的範圍 |
|---|---|---|---|
| 逐筆 | FitStore、`series_*`、成就逐筆、cptests、channel_peaks、workout_curves、mmp_cache、**自動分類逐筆值** | 只有那一筆 | 只有那一筆（刪掉它的條目） |

| 全歷史累加 | PMC、`tl()` | 那天以後全部，但很便宜 | 那天以後全部，但一年後的影響小於 10⁻⁴ |

## 4. 設計

### 4.1 分級：熱（≤ 90 天）、溫（≤ 1 年）、冷（> 1 年）

| 等級 | 範圍（擁有者筆數） | 什麼時候算 | 存哪 | 頁面行為 |
|---|---|---|---|---|
| **熱** | 近 90 天（54 筆） | **同步時立刻算**：解析、欄位、判讀、racepower 逐筆、自動分類、成就。L2 的熱窗（PD 最後一個格點、狀態、課表）同步後接著算 | L1 逐筆：以檔案雜湊為 key 的一列（建議 SQLite 的一張表，或每筆一個小 JSON），不要用「一個 key 一個大 JSON」 | 總覽、課表、活動列表、圖表「近 90 天」**只讀熱資料**，不等溫冷 |
| **溫** | 91～365 天（165 筆） | L1 在同步時已經是逐筆的，不必另外算；版本升級時**排在熱之後**背景補 | 同上，加上**月彙總段**（每月的 TSS 日序列、mean-max 外包線、TIS 加總） | 圖表預設 365 天：熱＋溫的月段合起來算 |
| **冷** | 一年以上（588 筆；其中 171 筆超過 3 年） | **看到才算**，或在背景最低優先補；SP-317 封存前先寫成**月摘要**（凍結，之後不再重算） | 月摘要（每天的 TSS、每月的 mean-max 外包線、成就或登頂摘要、每筆的 `workout_metrics`）；原檔依 SP-317 刪除 | 往前捲或選「全部」時才載入；第一次顯示「正在計算較舊的資料」 |

說明：

- 熱、溫、冷是**計算的優先順序**和**彙總段的封存方式**，不是三份不同的程式。L1 逐筆結果不分級，都以檔案雜湊為 key。
- 本機量測：熱的 54 筆全部判讀冷算 1.2 秒，溫的 165 筆 3.0 秒，冷的 588 筆 5.4 秒（已驗證）。只算熱的話，版本升級後的第一頁成本是 1/8 左右。

### 4.2 增量重算設計

1. **逐筆 key 改成「內容雜湊＋欄位版本＋該筆的輸入簽章」**（接 SP-308）。
   - FitStore 已經是這個形狀，只要把 (size, mtime) 換成 sha256。
   - `cached_series` 的條目也改用雜湊，並加上「計算函式的原始碼雜湊」（學 fitcache 的 `_h(func)`，只雜湊那個函式），取代手動升 `_vN`。
   - 好處：不用再記得升版本；改一個函式只重算那個欄位；檔案搬家或還原不會失效。
2. **自動分類改成逐筆**。
   - 每筆值的 key ＝（檔案雜湊、該筆的輸入：運動、標籤、RPE、當天門檻簽章、自己用到的 plan 測驗）＋各函式雜湊。
   - 只有跨活動的部分（例如「同一路線的歷史」）才看視窗。
   - 現在每筆的 stamp 已經寫進檔案，只是沒拿來用，改起來不大。
3. **門檻估算從「整份 key」改成「逐格點 key」**，比照 `PdMemo.sig(day)`：
   - 格點日 d 的 key ＝ d 以前的跑步（或它真正用到的窗）、d 當天的 plan 門檻、相關函式的雜湊。
   - 去掉 `today`：只有最後一個格點會隨今天改變。
   - 新增一筆時只重算那天以後的格點。刪三年前的一筆，只影響它所在窗的格點。
4. **程式版本只雜湊「真正計算的函式」**，不雜湊整個模組。
   - `PdMemo._prepare` 和 `_estimate_key` 現在雜湊整個 `athlete.py`、`thresholds.py`，`activity_auto._code_sig` 雜湊 9 個模組。
   - 改成列出各自呼叫的函式（像 `fitcache.versions()` 那樣）。代價是漏列依賴時會用到舊值，所以保留一個手動版本常數當保險。
5. **PMC 不需要做快取**。全歷史重算 0.02 秒（本機），維持每次重算，只要讓它讀的「每日 TSS」來自 L1 逐筆值，以及冷資料的月摘要。
   - 「從變動那天往後追加」帶來的效益太小，不值得增加複雜度（推估）。
   - `pmc_cache` 這張廢棄的表可以刪掉，或改用來存 SP-317 的封存日 TSS。
6. **最佳成績用「月外包線」合併**：
   - 每月存一條 mean-max 外包線，也就是該月每個時長的最大值。
   - 查某個時間窗 ＝ 完整月份的外包線取最大值，再和頭尾不完整月份的逐筆曲線取最大值。
   - 新增一筆：那個月的外包線和新曲線取最大值。刪一筆：只重算那個月。
   - 冷月份的外包線在 SP-317 封存時凍結。
7. **圖表渲染快取的 key 改成分段**：
   - 資料指紋只包含「範圍 [b − 預熱期, e] 內的活動清單雜湊」，加上範圍內用到的設定。預熱期：PMC 類取 6×42 天，其他取 0。
   - 程式簽章從 mtime 改成**檔案內容雜湊**，至少要做到這一步。更好的做法是每種圖只雜湊它用到的模組。
   - `today` 只放進範圍以 today 為端點的圖。
8. **舊值先顯示，背景再更新**（stale-while-revalidate）：
   - 圖表、狀態、自動分類在 key 失效時，如果有上一版的值，就先回舊值，標「更新中」，同時在背景排一個重算工作。
   - 自動分類已經這樣做（stale）。圖表和狀態也照做，部署後第一次開頁面就不會被卡住。
9. **同步時就地更新 Dataset，不換物件**：
   - 新增一筆就 `append` 到現有的 Dataset，更新 `first_day`、`last_day`。用一個「資料世代號」取代 `id(ds)` 當下游 key。
   - 這樣 `ds.memo`、狀態、課表裡跟這次變動無關的部分都能保留。
   - 這是最大的一塊工作（L），可以等前面幾項做完再看還需不需要。
10. **版本升級後在背景補算**：
    - 部署後不在暖機裡同步算完所有東西。順序是：先建熱資料的 L1 和熱窗的 L2，接著把溫、冷排進背景佇列，由新到舊補。
    - 補完一個 key 的新版，才刪掉舊版的 `series_*` 檔（解決 §2.4 的磁碟增長）。

### 4.3 多租戶排程（100 位會員）

- **全域重建佇列**，依優先序：
  1. 使用者正在等的頁面請求
  2. 同步後的熱資料
  3. 部署後的熱資料
  4. 溫資料背景補算
  5. 冷資料背景補算
- **同時重建的上限**：NAS 4 核心、10 GB 的情況下，「整份等級」的重建同一時間只跑 1 個，「單筆」工作最多跑 2 個（推估，依 `_pool_size` 現在給 2 個 worker，加上一個 Dataset 好幾百 MB）。
  - 用一個全域 semaphore 包住 `_build_dataset`、自動分類的工作、狀態計算。
- **部署後錯開**：
  - 不要一次暖完所有租戶。最近 7 天有登入或有同步的租戶，依最後活動時間排進佇列，每個做完才做下一個。
  - 其他租戶等第一次登入時才補，補的時候先回舊值。
  - SP-317 的每月封存已經定好 03:00～05:00 錯開執行，可以共用這個佇列。
- **同步尖峰**：每個租戶的同步只觸發「1 筆的 L1、熱窗的 L2」，本機約 1 秒（推估），NAS 推估 5 秒內。這部分本來就能同時跑好幾個；彙總由佇列做合併（同一個租戶 5 分鐘內多次同步只算一次）。
- **記憶體**：`DATASETS_MAX=2` 改成「依記憶體預算的 LRU」，搭配就地更新（§4.2-9），一個租戶只保留一個 Dataset。冷租戶的 Dataset 釋放掉，下次從 FitStore 暖載入，本機 0.1 秒，NAS 推估 0.5 秒左右。
- **先修正確性**：`hrc_test` 的 key 加上租戶；`plan_sessions._cache` 的 key 加上租戶 id。

## 6. 結論與後續

### 6.1 結論

- FIT 解析和逐筆快取已經是增量的。慢是因為上層的快取用「整份資料、整個模組、`id(ds)`、今天」當 key，加上部署頻繁、版本常升，所以「一點變動 → 整份重算」幾乎每天都在發生。
- 最划算的做法是**先改 key、再把重算移到背景並先回舊值**。真正的分級儲存（熱、溫、冷，月摘要）放在第二階段，和 SP-317、SP-308 一起做。

### 6.3 要使用者決定的問題

1. **圖表預設時間範圍**：現在是 365 天。要改成預設 90 天（只讀熱資料，最快），還是維持 365 天（熱加溫）？
2. **先顯示舊值**：部署或版本升級後，可以先看到舊版的圖表和判讀，加上「更新中」的標示，等幾十秒到幾分鐘後自動換成新的嗎？還是寧可等，也要一開始就是新的數字？
3. **冷資料（一年以上）第一次查看**可以等多久？例如 10 秒內並顯示進度，可以接受嗎？
4. **NAS 實測**：本文的 NAS 時間是用本機 × 4～6 推估的。要不要允許在 NAS 容器裡跑一次唯讀量測腳本（不寫入、不讀金鑰，只讀 FIT 和快取），取得真實的倍率？這次這個動作被權限擋下了。
5. **多租戶部署後的補算順序**：可以接受「最近 7 天有登入或同步的會員先補，其他人等第一次登入才補（先看到舊值）」嗎？
6. **SP-317 的範圍**：單上寫擁有者的資料大約從 2023 年開始，但實際上 2020～2022 年有 40 筆、2023 年也有一部分；以今天為準，超過 3 年的共 171 筆。確認這些會在第一次封存時刪掉嗎？
7. **同步「列出活動」每次 33～54 秒**（檢查全部 819 筆）。這個不屬於快取，要放到 SP-303，還是另外開一張單？

## 7. 開放問題（給 SP-303 Fable 調查）

1. NAS 和本機的真實速度倍率是多少（本文假設 4～6 倍）？要在容器裡用同一份 `bench.py` 跑冷解析、估算、判讀、圖表，才能確定。
2. FIT 解析是純 Python 的 fitdecode，本機每檔約 0.12 秒。換成 C 或 Rust 的解析器能快 10 倍嗎？要用 812 個檔做 parse-only 的 profiling 和替代解析器的原型比較才知道。
3. `tis-load`（`tl(tisaerobic)`）在逐筆值已暖時還要 2.2～3.7 秒，而且 90 天和 365 天一樣慢。熱點是在 evaluator 逐筆累加，還是在 TIS 逐秒計算？要對單張圖做 cProfile。
4. `LazyFiles` 把 npz 轉成 Python list（每個樣本約 32 bytes）。如果全程維持 numpy，記憶體和時間能省多少？要比較圖表頁的 tracemalloc 和 RSS。
5. 啟動時的慢請求（`/plan` 18.9 秒、feasibility 17.9 秒）是在排隊等 single-flight 的 Dataset 鎖，還是跟暖機執行緒搶 GIL？要記錄每個請求等鎖的時間。
6. 多 MB 的 `series_*.json` 用 `json.dumps` 整檔重寫會長時間占住 GIL。改成 SQLite 逐列寫入能讓請求延遲降多少？要在 NAS 上量 7 MB 檔案 flush 的時間和那段時間的請求延遲。
7. 同步「列出活動」每次 33～54 秒，檢查 819 筆。COROS 的列表 API 能不能從上次的游標開始拿，或用更大的分頁？要看 API 呼叫的次數和分頁的 trace。
8. 同步「收尾」有一次 64.6 秒，另一次 0.9 秒。是 `refresh_hr_profile`、feel passes，還是 dedup 造成的？要在收尾裡分步計時。
9. 4 核心的 NAS 上把 AnyIO 執行緒上限設成 200，會不會造成 GIL 搶占、讓延遲變長？要用並發 10～20 個圖表請求的負載測試比較。
10. 改用多個 process 的 worker（uvicorn workers 大於 1），或 Python 3.13 free-threaded，搭配目前的記憶體快取，划算嗎？要在 NAS 上比較吞吐量和記憶體。
11. 2026-10-05 卡在「第 9／17 筆」時的實際記憶體峰值和容器上限是多少？容器的記憶體上限這次沒有讀到，要看 `docker stats` 和那時的 OOM 紀錄。
12. 活動自動分類 807 筆要 6.1 秒（本機，判讀已暖）。是哪個模組最慢（racepower 的 trailhr、maximal，或 intensity）？要對 `compute_blocking` 做 profiling。
