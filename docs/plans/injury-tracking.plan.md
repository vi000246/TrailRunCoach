# Plan：傷病紀錄與「哪些訓練跟受傷有關」分析

- 日期：2026-10-02
- 狀態：**設計，尚未實作**（這份只有文件，沒有改程式）。
- 分支基準：`feat/overview-racepower-ui`
- 類型：feature；Size：M–L（分 5 個階段，§7）
- 相關：`docs/research/validation-lovdal.md`（Lövdal 2021 驗證護欄）、`docs/research/impact-cadence.md`（ILR × 步頻）、`docs/research/detraining.md`（停訓後恢復期）、`docs/plans/auth-and-demo.plan.md`（示範模式）

## 背景

擁有者的需求（2026-10-02）：「在活動資訊上，讓我標記有沒有受傷之類的，像活動自評（RPE）那樣，這樣就能分析哪些活動造成受傷、哪些指標看得出來。設計怎麼做。」

有兩件事要先講清楚：

1. **受傷是一段期間，不只是某次活動的屬性。** 膝蓋痛通常是累積出來的，在「某一次跑步」才第一次感覺到；之後會痛好幾天、減量或停跑、再慢慢回來。所以資料要分兩層：**活動上的一鍵疼痛標記**（像 RPE，觀察值），以及**傷病事件**（有開始、有結束、有部位與嚴重度）。一鍵標記會自動接到事件上，擁有者不必另外填表（§1.3）。
2. **個人資料能分析出的東西很有限。** 業餘跑者一年大概 1–4 次「影響訓練」的傷。Lövdal 2021 用 74 人、575 次受傷，最好的單一指標 AUC 也只有 0.57（`validation-lovdal.md` §0）。所以 app 只能說「你前幾次受傷之前，這些指標比你平常高」，不能說「這個指標會讓你受傷」。這條誠實規則寫在 §3.4，所有分析結果都標**推估**。

限制：只有手腕光學心率，沒有胸帶（強度相關指標要容忍誤差，§3.2）；Stryd 只有部分路跑有（ILR、衝擊 G 只在有 Stryd 的活動）；鞋子目前沒有資料，不做。

## 0. 決策摘要

| 問題 | 建議 | 理由 |
|---|---|---|
| 資料怎麼存 | 新表 `injury_events`（事件）＋ `activity_tags` 加 3 個欄位（`pain`、`pain_area`、`injury_id`） | 活動標記沿用 `activity_tags` 的 key（開始分鐘＋檔名）、批次編輯、late column 遷移，不另寫一套比對；事件有自己的生命週期，不能塞在活動列上 |
| 一鍵 UX 怎麼接事件 | 活動頁點「痛」：同部位有進行中的事件就接上；沒有就建一筆**草稿事件**（開始日 = 這次活動），細節之後再補 | 擁有者要的是「像 RPE 一樣點一下」；事件細節（側邊、類型、結束日）都可以晚點補 |
| 「痠」算不算受傷 | 不算。「痠」只存在活動上，不建事件；分析時另外當一個「痠的頻率」指標 | 練完痠是正常的適應，算成受傷會灌爆事件數 |
| 嚴重度 | 必填 3 級，用**對訓練的影響**定義：輕 = 照練、中 = 減量或改練、重 = 停跑；疼痛 0–10 選填 | 「影響訓練」才是分析要的定義（OSTRC 問卷的做法，Clarsen 2013；對應方式推估）；0–10 每次感覺不同，當選填 |
| 分析設計 | **同一個人的 case-crossover**：每次受傷前 21 天 vs 同一人其他時間的 21 天（每 7 天取一個對照窗，排除傷前傷後） | 個人只有一個人，不能跨人比較；同人比較自動控制了體質、跑姿、鞋子 |
| 事件太少 | < 5 次：只有描述（「你受傷前，這些比平常高」），不給 p 值、不給 OR；5–14 次：加「幾次中有幾次高於平常」；≥ 15 次：才給 OR 與 CI | §3.4 |
| 回饋到課表 | 「跟你受傷前很像」的提醒**預設關閉**，打開也只是資訊、不擋課；受傷停跑後回來接既有的 `reentry`（恢復期） | 個人資料的 AUC 不會比 Lövdal 好；不能讓雜訊擋課 |
| 隱私 | 只存在本機 DB；分享連結、示範模式、AI 教練（未經同意）都不包含 | 健康資料 |

## 1. 資料模型

### 1.1 活動上的一鍵標記（`activity_tags` 新欄位）

`backend/engine/activity_tags.py:129` 的 `LATE_COLS` 加三欄（`database._migrate_schema` 和 `upsert` 都會補上），`backend/db/models.py:231` `ActivityTag` 同步加：

| 欄位 | 型別 | 值 |
|---|---|---|
| `pain` | INTEGER NULL | NULL = 沒填；0 = 沒痛（明確點過）；1 = 痠；2 = 痛（影響跑姿或配速，或跑完還在痛）；3 = 痛到中斷 |
| `pain_area` | TEXT NULL | `AREAS` 的 key（§1.4），NULL = 沒指定 |
| `injury_id` | INTEGER NULL | 接到哪筆 `injury_events`（NULL = 沒接） |

- `TAG_FIELDS`（`backend/api/workouts.py:104`）加 `pain`、`pain_area`、`pain_side`（`pain_side` 不存在活動列，只在建草稿事件時帶過去）；`ActivityUpdate` 加對應欄位；`validate()` 加 `INVALID_PAIN`、`INVALID_AREA`。
- **NULL 和 0 要分開**：「沒填」不能當成「沒痛」。分析時把 0 當成確認的健康日，NULL 當未知（§3.3）。
- 「沒痛」（0）這一格可以批次設定（`PATCH /activities` 的 `items`），讓擁有者補標過去一段時間「這幾週都沒事」。

### 1.2 傷病事件（新表 `injury_events`）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | INTEGER PK | |
| `athlete_id` | INTEGER | 預設 1（和其他表一致） |
| `area` | TEXT | `AREAS` 的 key；草稿可以是 `unknown` |
| `side` | TEXT NULL | `left` / `right` / `both` / NULL（下背、其他不用填） |
| `kind` | TEXT | `overuse` 過度使用（慢慢痛起來）/ `acute` 急性（跌倒、扭到、撞到）；預設 `overuse` |
| `severity` | TEXT | `mild` 輕（照練）/ `moderate` 中（減量或改練）/ `severe` 重（停跑） |
| `pain_max` | INTEGER NULL | 最痛的時候 0–10（選填） |
| `onset_date` | TEXT | `YYYY-MM-DD`，開始痛的那天 |
| `onset_key` | TEXT NULL | 開始痛的那次活動（`activity_tags` 的 key，`YYYY-MM-DDTHH:MM`）；沒有就是休息日開始痛 |
| `onset_file` | TEXT NULL | 那次活動的 dataset 檔名（比對時先比檔名，同 `activity_tags.find`） |
| `status` | TEXT | `draft`（一鍵建的，細節沒補）/ `active` / `resolved` |
| `resolved_date` | TEXT NULL | 好了的那天（可以回填） |
| `days_missed` | INTEGER NULL | 使用者自填的停跑天數；NULL = 用自動算的（§1.5） |
| `pause_quality` | BOOLEAN | 「受傷期間暫停強度課」（§4.2），預設 false |
| `note` | TEXT NULL | 自由文字（例如「下坡右膝外側」「看過復健科：髂脛束」） |
| `created_at` / `updated_at` | DATETIME | |

- **沒有 FK 到活動**：活動用開始分鐘當 key（`activity_tags` 的既有做法），因為大多數 WKO5 活動沒有 `workout_files` 列。
- 新表由 `init_db` 的 `create_all` 建立（`database.py:19` 註解：新表不用寫進 `_migrate_schema`）。
- 選填的**每日紀錄** `injury_logs`（`event_id`, `date`, `pain` 0–10, `note`）放在 P4：休息日也能記「今天早上還痛 3 分」，回跑判斷用（§4.3）。P1–P3 不需要它，活動上的 `pain` 就夠了。

### 1.3 一鍵標記和事件怎麼接（`engine/injuries.py` 的 `attach()`）

在活動頁點了 `pain` 之後（純函式，測試好寫）：

1. `pain` 是 NULL、0 或 1（痠）：不碰事件。之前若有接到事件，`injury_id` 清掉；如果那筆是 `draft` 且沒有其他活動接著，草稿刪掉（點錯可以反悔）。
2. `pain` ≥ 2：
   - 找同一個 `pain_area`（沒指定就不限部位）、`status` 為 `draft` / `active`、`onset_date` 在這次活動之前 0–28 天內（推估）的事件 → 接上（`injury_id`）。
   - 找不到 → 建一筆 `draft`：`onset_date` = 這次活動的日期、`onset_key` = 這次活動、`area` = `pain_area` 或 `unknown`、`severity` = `mild`（`pain` = 3 時是 `moderate`）、`kind` = `overuse`。
3. 一次活動只接一個事件。兩個部位同時痛很少見；真的有，就在傷病紀錄頁手動多建一筆。
4. 如果使用者改了事件的 `onset_date` 到更早（「其實上週就開始了」），`onset_key` 改成那天的活動（有的話）。

`resolved` 的事件不會自動被接上。好了又痛 → 建新事件，並自動在 `note` 加「距上次 XX 天、同部位」，分析時標成**復發**（§3.3 的排除規則）。

### 1.4 部位清單（固定、短）

`AREAS = {"knee": "膝", "shin_calf": "小腿／脛骨", "achilles": "阿基里斯腱", "ankle": "腳踝", "foot": "足底／腳跟", "hip": "髖／臀", "thigh": "大腿", "low_back": "下背", "other": "其他"}`

- 擁有者的建議清單是「膝／小腿／腳踝／足底／髖／下背／其他」。多加的兩個：**阿基里斯腱**（跟爬坡、小腿負荷有關，和膝的機制相反，合在小腿會讓分析混在一起）、**大腿**（腿後肌拉傷是另一種急性傷）。要不要留由擁有者決定（§9）。
- 膝蓋外側（髂脛束）、前側（髕股）不拆，寫在 `note`。拆太細，每一格都只有 0–1 次，分析沒用。

### 1.5 自動算的「停跑天數」

`days_off_auto` = 從 `onset_date` 到之後第一次「`pain` ≤ 1 或沒填，且時間 ≥ 20 分」的跑步之間的天數，減掉擁有者平常本來就不跑的天數（傷前 4 週的平均休息天比例 × 期間天數，推估）。`days_missed` 有填就用填的。

疼痛 (?)   [ — ] [ 痠 ] [ 痛 ] [ 中斷 ]          ← 4 顆 segmented 按鈕，點一下就存

## 3. 分析

### 3.1 單位：每日暴露序列（`engine/injury_exposure.py`）

從 Dataset 算一份「每天」的暴露（休息日 = 0），再從它算各種視窗。只用 dataset 已有或 workout_review 快取裡已有的東西，不另讀 FIT。

| 指標 | 來源 | 每日值 | 備註 |
|---|---|---|---|
| 跑步時間、距離 | `w.metrics` duration / distance | 加總 | 只算跑步（路跑、越野、跑步機） |
| 負荷 TSS | `w.metrics` tss | 加總 | CTL／ATL 用既有的 PMC（`panels/fatigue.pmc`） |
| 爬升、**下降**公尺 | `climbing`、`descending`（`evaluator.WORKOUT_METRICS`） | 加總 | 下降是膝蓋的主要候選 |
| 陡下坡時間（坡度 < −10%） | `workout_review.downhill_share`（:1288） | 加總 | 需要該活動的 review 快取；沒有就 NULL |
| 衝擊量（ILR·時間） | `downhill_share` 的 ILR 積分、`impact_per_km`（:1095） | 加總 | **只有 Stryd**；沒有 Stryd 的天 = 未知，不當 0 |
| 步頻 | review 快取的 cadence 中位 | 時間加權平均 | 手錶也有（加速度計） |
| 越野佔比 | `athlete.is_trail` | 越野時間 ÷ 跑步時間 | |
| 低強度佔比 | 心率 < AeT 的時間（既有的強度分配） | 21 天合計 | 手腕光學：見 §3.2 |
| 長跑天 | 單次 ≥ 90 分（徐國峰 90 分鐘檢查長度；推估）或 ≥ 該週 30% | 0／1 | |
| B2B 天 | `engine/b2b.py` 的判定（連兩天長天） | 0／1 | |
| 負重天 | `racepower/athlete.activity_pack`（`pack_kg` > 0） | 0／1、kg·時 | |
| 登山／健行時間 | sport_type hiking / mountaineering | 加總 | 不算進跑步時間，但下降公尺要算 |
| 努力度「全力」天、RPE | `activity_tags` effort、手錶 RPE（`load_recorded`） | 0／1、平均 | RPE 很少（只有舊的 Garmin 檔有），有就用 |
| 痠的次數 | `pain = 1` | 次數 | 「痛之前是不是先痠了好幾次」 |

從每日序列算的視窗指標（onset 前的視窗都**不含** onset 當天）：

- 7／14／21 天合計：跑步時間、距離、下降、陡下坡時間、衝擊量、長跑天、B2B、負重天、全力天。
- **週增量**：W0（d−7…d−1）對 W1（d−14…d−8），和 **W1 對 W2**（延遲一週：Lövdal 的 OR 1.41 出現在增量後第 8 天，`validation-lovdal.md` §3.1）。前一週太小（< 4 週平均的 60%）不算（同文件 §5 的分母建議）。
- **2 週平均增幅**：(W0 − W2) ÷ (W1 + W2)（Lövdal 最好的負荷變化指標之一，AUC 0.546）。
- **CTL ramp**：onset 前 7 天的 CTL 變化。
- **ACWR**（7:28 uncoupled）：**只畫在圖上**，不進 §4 的提醒（Lövdal：不要當受傷預測，`validation-lovdal.md` §3.4）。
- **Monotony**（Foster）：前 7 天、前 14 天的最大值。
- **低強度佔比**：前 21 天。
- **步頻**：前 21 天的時間加權平均，相對於自己 26 週的中位（差多少 spm）。
- **越野佔比**：前 21 天。

### 3.2 手腕心率與缺值

- 只有光學心率：低強度佔比用「< AeT − 3 bpm」才算低強度、「> AeT + 3」才算高強度，中間的時間不算（`workout_review.AET_MARGIN` 的 3 bpm，推估），避免光學心率的跳動讓佔比亂飄。強度相關的指標在畫面上加 `?`：「用手腕光學心率算，誤差比胸帶大」。
- 優先用不靠心率的指標：時間、距離、下降、坡度、步頻、越野佔比。
- 缺值（沒 Stryd、沒有 review 快取）的指標：該視窗標「未知」，不補 0；一個指標在 < 60% 的視窗有值時（推估），結果卡片上這一列變灰，寫「資料不夠」。

### 3.3 設計：同一個人的 case-crossover

每個納入的事件 = 一個 **case 視窗**（onset 前 21 天）。對照 = 同一個人的 **control 視窗**：

- 從資料第一天起，每 7 天取一個 21 天視窗（Lövdal 敏感度分析「每週 1 天」的做法，降低重疊）。
- 排除：
  - 任何事件 `onset_date` 前後 28 天內的視窗（傷前的負荷不能同時當對照）；
  - 任何事件進行中（`onset` 到 `resolved`）以及好了之後 42 天內的視窗（回歸期跑量會大增，`validation-lovdal.md` §3.6）；
  - 視窗內跑步 < 3 次或 < 2 小時的視窗（不在「有在練」的狀態；推估）；
  - 有接到事件的活動裡標 `pain` ≥ 2 的天落在視窗內的。
- 納入的事件：`kind = overuse`、`severity` ≥ 中（「輕 = 照練」可以選擇納入，預設不納入：照練的痛常常是痠，雜訊大）；**復發**（同部位、上次好了之後 42 天內）預設排除；`draft` 不納入（細節沒補，不知道是不是真的傷），頁面上提示「補完細節才會進分析」。
- `acute`（跌倒、扭到）不進負荷分析，只看「發生在什麼地形、累了沒」（onset 那次活動的越野與否、第幾小時、下降公尺），另外一張小卡描述。
- 對照日期範圍：預設整段資料；選項「只比同一季（± 3 個月）」，避免夏季、比賽季的系統差異。

**每個指標的計算**：case 視窗的值，在所有 control 視窗中的**百分位**（0–100）。百分位不需要分佈假設、對 n 小也合理，而且可以跨指標比較。

**部位對應的指標**（排序用，推估）：膝 → 下降、陡下坡時間、衝擊量、步頻；阿基里斯腱、小腿 → 爬升、越野佔比、強度、步頻；足底 → 路跑距離、週增量；髖、下背 → 長跑、負重。結果頁先列跟該部位有關的指標，但全部指標都看得到，不藏結果。

### 3.4 n 小的誠實規則（`injuries.honesty_tier(n)`）

| 納入事件數 n | 顯示 | 不顯示 |
|---|---|---|
| 0 | 「還沒有足夠的紀錄」＋ 怎麼記的說明 | 任何分析 |
| 1–4 | 每個指標：case 的百分位點，文字「你受傷前，X 在你自己的第 85 百分位（比平常高）」；整體標**推估、描述而已** | p 值、OR、CI、「風險」這個詞、「造成」這個詞 |
| 5–14 | 加：中位百分位，和「n 次中有 k 次高於你的中位」 | p 值、OR |
| ≥ 15 | 加：同人 conditional logistic（每次一個指標，對照窗 1:m）的 OR 與 95% CI，BH 校正，標「探索性」 | 多指標模型、預測分數 |

- 文字一律用「受傷前這些比較高」，不用「造成」「導致」。圖表標題下面固定一行：「同一個人、次數很少，只能看出巧合還是規律的方向，不能證明因果。推估。」
- 對照視窗 < 20 個時（資料太短），百分位加註「對照少」。
- 「高於平常」的定義：≥ 第 75 百分位（推估）。

### 3.5 圖

1. **時間軸**（§2.3 的主圖）：每週跑步時間長條 ＋ CTL 線 ＋ 傷病色帶 ＋ 痠痛刻度。可切換長條為「下降公尺」「衝擊量」「越野時間」。ACWR 可以疊成細線（標「只參考，不預測受傷」）。
2. **傷前 vs 平常（點圖）**：每一列一個指標（左邊指標名 ＋ `?`）；灰色帶 = control 視窗的 P25–P75，灰色細線 = P10–P90，中間一條 = 中位；每次受傷一個彩色點（顏色 = 部位），滑過顯示日期與數值。列依「case 點的中位百分位」由高到低排序。n < 5 時點旁邊不寫任何統計量。
3. **單次事件卡**：點時間軸上的一筆傷，展開「前 21 天」小圖：每日跑步時間長條，下降公尺疊線，onset 那天紅線；下方一行列出這次最高的 3 個百分位（例如「下降 P96、陡下坡 P90、週增量（延遲一週）P88」）。

## 4. 回饋到課表

### 4.1 「跟受傷前很像」的提醒（預設關閉）

- 設定：`user_settings` 的 `injury.pattern_alerts`，預設 `false`；設定頁「傷病」區塊一個開關，`?` 寫明「只是提醒，不會改課表，也不會擋課」。
- 條件（全部成立才提醒，推估）：
  - 納入事件 n ≥ 5（§3.4 的第二級以上）；
  - 該指標是「個人型態」：中位百分位 ≥ 75，且 ≥ 2/3 的事件高於中位；
  - **現在**的 21 天視窗（含未來 7 天已排的課，用課表的預估時間、爬升）在同一個對照分佈裡 ≥ 第 85 百分位；
  - ACWR、monotony 不列入（Lövdal：不當護欄）。
- 顯示：浮動建議框（`engine/suggestions.py`）新類型 `injury_pattern`，資訊類、只有 ✕（同 `zone_update`），id = `injury_pattern:<metric>:<week>`。文字範例：「你前 6 次膝蓋受傷，有 5 次之前的下降公尺偏高（推估）；這 3 週的下降在你的第 90 百分位。」
- 不重複既有護欄：週增量 > 20%、CTL ramp、低強度佔比已經在 `quality_gate`（:88–89）處理，提醒裡不再說一次。

### 4.2 傷病進行中

- `status = active` 且 `severity = severe`（停跑）：建議框出現「要不要把今天起 7 天設成不排課日期？」（`engine/blackouts.py`；接受才寫入，不自動改）。
- `pause_quality = true`（事件 dialog 的勾選）：`quality_gate` 加一個原因 `injury`（「傷病紀錄 #12 進行中：先不排間歇」，`block=True`），直到事件 resolved。預設不勾，因為「輕」的痛照練是常態。
- 週計畫的週註記（`blackouts.week_note` 同類）加一行「右膝進行中（第 5 天）」，讓排課的人看得到。

### 4.3 回跑（接 `engine/reentry.py`）

- 停跑造成的空檔，`reentry.find`（:259）已經會從活動資料偵測（≥ 6 天沒跑 → Daniels 表 9.2 的恢復期）。傷病只加三件事：
  1. 空檔和事件重疊時，恢復期的說明改成「傷停 N 天」，來源加上事件連結（`text_of` 多一個參數）。
  2. **傷停的恢復期往上一級**（例如停 10 天照 14–28 天那一級排；推估）：傷後回來不只是體能，組織也還沒適應負荷。這條預設開、可以在設定關。
  3. 恢復期內每次跑完，活動頁的疼痛列高亮提醒「記一下有沒有痛」；如果恢復期內又點了「痛」，建議框出現「先維持這週的量，不要往上加」（資訊）。疼痛監測的門檻（跑時 ≤ 5/10、隔天早上回到原本的程度）參考 Silbernagel 2007 的阿基里斯腱疼痛監測模型（**未驗證**：需要重讀原文確認數字，且只研究過阿基里斯腱）。
- 「輕」「中」不會產生空檔，不觸發 reentry；它們只靠 §4.2 的註記。

## 5. 隱私

- **只存在本機**：`injury_events` 和 `activity_tags.pain*` 在 `~/.wko5coach/wko5coach.db`，不同步到 COROS／TP，不推到手錶。
- **分享連結**（`engine/racepower/share.py`）：已經是白名單快照，而且丟掉計畫的警示文字；加一個測試確定任何 `injury` / `pain` 欄位不會出現在快照裡（白名單之後被改時也會擋下來）。
- **示範模式**（`auth-and-demo.plan.md`）：示範資料不放任何傷病；傷病紀錄頁和活動頁的疼痛列在示範模式**隱藏**（API 回 404）。要不要放一組虛構事件展示功能，由擁有者決定（§9）。
- **AI 教練**（`todo-ai-coach-ai-coach-training-analysis.plan.md`、`api/ai.py`）：送出的內容預設不含傷病；設定裡另一個開關「讓 AI 教練看傷病紀錄」，預設關。
- **匯出／備份**：DB 備份照舊包含（是擁有者自己的資料）；之後若做「匯出給別人看」的功能，傷病預設不勾。
- 頁面固定一行小字：「這不是醫療診斷。持續或加重的疼痛請看醫師或物理治療師。」

## 6. 測試策略

照 memory 的規則：**不依賴 WKO5 資料夾、不讀真實 DB**；全部用合成資料或 `tmp_path` 的 SQLite。不碰 port 8000（API 測試用 `httpx.AsyncClient(app=…)` 或 FastAPI `TestClient`，DB 路徑指到 `tmp_path`）。

| 層 | 測試 |
|---|---|
| 存取 | `test_injuries_store.py`：建立、改、resolve、刪除；`activity_tags` 舊表（沒有新欄位）讀得到、upsert 會補欄位（同 `LATE_COLS`）；`_default_db` 在測試裡被擋住（沿用 `test_activity_tags.py:98` 的做法） |
| 接事件 | `attach()` 純函式表格測試：痠不建事件、痛建草稿、28 天內同部位接上、29 天建新的、resolved 不接、改回「—」刪掉孤兒草稿、復發標記 |
| 暴露 | 合成 Dataset（沿用 `test_activity_tags.py` / `test_quality_gate.py` 的假 dataset 寫法）：已知每日時間、下降、Stryd 有／無 → 每日序列、7/14/21 天合計、週增量（含分母太小不算）、沒 Stryd 是 NULL 不是 0 |
| case-crossover | 合成 2 年資料，埋 6 次事件，每次前面放一段 +30% 的週增量 → case 百分位高、對照視窗排除規則（傷前後 28 天、回歸期 42 天、低量週）都有效；隨機事件 → 百分位接近均勻 |
| 誠實規則 | n = 0／3／7／20：回傳的欄位（`tier`、有沒有 `p` / `or`）；n < 5 的 JSON 裡**不能有** `p`、`or`、`ci` 鍵；文字不含「造成」「導致」 |
| 回饋 | 提醒預設關；開了但 n < 5 不提醒；ACWR 永遠不觸發；`pause_quality` 讓 `quality_gate` 擋間歇、resolve 後解除；傷停的 reentry 往上一級 |
| 隱私 | 分享快照不含 `injury` / `pain`；示範模式下傷病 API 404；AI 教練的 payload 預設不含傷病 |
| 前端 | Playwright 對合成資料啟動在**其他 port**（例如 8765）的 app：點「痛」→ 出現連結 chip → 傷病紀錄頁出現草稿卡 → 補細節 → 好了 |

## 8. 不做的事

- 不做受傷「預測分數」或風險百分比：個人資料做不到，Lövdal 的群體模型也只有 AUC 0.57–0.72。
- 不做鞋子：目前沒有資料來源。之後若接 Strava／Garmin gear 再加一個暴露指標。
- 不做睡眠、HRV：目前的資料來源沒有（COROS FIT 沒帶，`activity_tags.py` 的 RPE 掃描也說明了 COROS 檔案的欄位很少）。之後有就加進 §3.1 的表。
- 不自動改課表：所有回饋都是建議或資訊，只有擁有者勾了 `pause_quality` 才會擋課。

## 9. 要擁有者決定的事

1. **部位清單**：用 §1.4 的 9 個（多了阿基里斯腱、大腿），還是照你原本的 7 個？
2. **嚴重度**：用「輕＝照練／中＝減量或改練／重＝停跑」三級（建議），還是要 0–10 必填？
3. **「輕」的痛要不要進分析**：預設不進（雜訊大）；如果你的傷大多是「照練但會痛」，就要改成納入。
4. **傷病紀錄頁放哪**：新的一頁（建議，導覽「活動」群組裡）還是活動編輯頁的一個分頁？
5. **「跟受傷前很像」的提醒**：同意預設關、n ≥ 5 才能開嗎？
6. **傷停後恢復期往上一級**：預設開（建議）還是預設關？
7. **示範模式**：完全隱藏傷病功能（建議），還是放一組虛構事件展示？
8. **過去的傷要不要回填**：如果你記得過去 1–2 年的幾次傷（大約日期、部位），P1 上線後先補，分析才有東西看。
